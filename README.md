# data-incremental-load-lab

![ci](https://github.com/Supp3r-Man/data-incremental-load-lab/actions/workflows/ci.yml/badge.svg)

Idempotent **incremental loads with DuckDB**, compared on a seeded multi-day simulation: full reload, watermark, watermark with a lookback window, key-diff delete sweep, and hash-diff MERGE, each scored against a **ground-truth full reload** for rows missed, stale, duplicated and left behind, plus what each one costs per run. Also: partition-overwrite backfills, rerun safety, and crash-mid-load atomicity.

> **What is verified, and what is not.** 45 tests pass locally on Python 3.13 (DuckDB 1.5.6), including seeded tests that compare every strategy with the ground truth. The GitHub Actions workflow (Linux, Python 3.11 and 3.13) ran green after the first push. I broke 8 key behaviours on purpose (lookback window, delete detection, hash comparison, default atomicity, watermark advance, the insert guard, the simulator's late rows, the backfill partition key) and the tests failed for all 8. **The data is synthetic and fictional**, generated by a small simulator with rates I chose, in an in-memory single-process DuckDB. The numbers show how the strategies rank on *this* workload; they do not show absolute speed, bytes read, behaviour at warehouse scale, concurrent writers, or your source's real lateness distribution. "Scanned" is a logical row count, not I/O.

## Measured results

`python -m incload demo` (seed 7, 20 days, 1,000 initial rows, per day: 60 new, 40 updates, 10 silent updates that do not bump `updated_at`, 8 soft deletes, 8 hard deletes, 15 late-arriving rows stamped 1-6 days old; 2,340 source rows at the end):

| strategy | missed | stale | ghost | dup | scanned/day | written/day | rerun-safe |
|---|---:|---:|---:|---:|---:|---:|---|
| full_reload | 0 | 0 | 0 | 0 | 1704 | 1704 | yes |
| watermark_append (insert-only, no key) | 222 | 128 | 178 | 894 | 108 | 108 | **no** |
| watermark (`updated_at >` high mark, upsert) | 222 | 128 | 149 | 0 | 108 | 108 | yes |
| watermark_lookback3 | 44 | 105 | 158 | 0 | 546 | 546 | yes |
| lookback3_sweep (+ key anti-join) | 44 | 105 | 0 | 0 | 2250 | 554 | yes |
| merge_hashdiff | 0 | 0 | 160 | 0 | 1704 | 133 | yes |
| merge_hashdiff_del | 0 | 0 | 0 | 0 | 1704 | 141 | yes |

`missed` = in the source, absent from the target. `stale` = in both, values differ. `ghost` = hard-deleted in the source, still in the target. `dup` = extra copies of a key. Cost is the mean over days 1-20 (day 0 is the initial load). `written` counts rows inserted or updated, plus rows removed by explicit delete detection; a truncate or partition drop is free.

What the table says on this workload:
- Plain watermark is the cheapest (about 6% of the full-reload scan) and also wrong three ways: late rows (missed), silent updates (stale), hard deletes (ghost). Soft deletes work, because they are ordinary updates.
- A 3-day lookback cuts missed rows from 222 to 44 for 5x the scan, and rewrites unchanged rows every run. It cannot fix rows later than the window, silent updates or hard deletes.
- The key sweep fixes hard deletes, but counted in rows it scans more than a full reload (2,250 vs 1,704). Keys are narrower than rows, so in bytes it could be cheaper; this lab does not measure bytes.
- Hash-diff MERGE reads everything but writes about 8% as many rows as a full reload and is the only incremental strategy that matches the truth, and only with delete detection on.
- Append-only is shown to make the point, not as the fair baseline: the fair watermark baseline is the upsert row above it.

Crash mid-load on day 3 (rows in the target):

| strategy | in a transaction | before | after crash | after rerun |
|---|---|---:|---:|---:|
| full_reload (crash after its delete) | yes | 334 | 334 | 401 |
| full_reload | no | 334 | **0** | 401 |
| watermark (crash after writes, before the watermark moves) | yes | 321 | 321 | 386 |
| watermark | no | 321 | 386 | 386 |

The non-transactional watermark load survives only because its writes are idempotent upserts and the watermark moves last. Backfill by partition overwrite on `created_day` repairs only the range it covers: the last 7 days took the watermark target from 499 bad rows to 430; all days took it to 0 at full-reload cost.

## Run

```
pip install duckdb pytest
python -m pytest                 # 45 tests, about 10 s
python -m incload demo           # prints the tables above
python -m incload demo --seed 3 --days 30
```

## Design notes

- Every strategy is `fn(env, ctx) -> Stats` and runs inside `run()`, which wraps it in one transaction: data writes and the watermark update commit together or not at all. `run(..., atomic=False)` and `crash_at=` exist to show what breaks without it.
- Upsert is UPDATE then INSERT-if-absent by key. Rerun safety is tested by restoring the pre-run watermark and replaying the same window.
- The watermark is the max `updated_at` of the rows pulled, not the wall clock.
- Partition overwrite must partition on an immutable column. Partitioning on `updated_at` hits the primary key when a row has moved partitions, and the transaction rolls back (tested).

## Layout

```
incload/sim.py     seeded source simulator (inserts, updates, silent updates, soft/hard deletes, late rows)
incload/loads.py   strategies, run() with transaction, diff vs ground truth, rerun check, partition overwrite
incload/bench.py   multi-day simulation, crash and backfill demos, table rendering
tests/             sim, strategy behaviour, atomicity, partition overwrite, seeded comparison with ground truth
STEPS.md           how this was built, and how to run it
```

## Known gaps

- One workload and mostly one seed shown; the seeded tests also run seeds 1 and 2 but only assert the ordering, not the magnitudes.
- Lateness is capped at 6 days and a lookback of 3 days is an arbitrary choice; real sources have long tails.
- Not modelled: concurrent writers during a load, source schema changes, clock skew between source and loader, equal-timestamp ties at the watermark, rows updated twice between loads (the upsert handles it, but it is not measured).
- MERGE is written as UPDATE plus INSERT in a transaction, not DuckDB's `MERGE INTO`.
- No CDC or log-based comparison; hard deletes are found only by diffing keys.
- Cost is logical rows. DuckDB itself scans the whole source to evaluate `updated_at >`; no index or partition pruning is modelled.
